# P0.4 Google OAuth Verification

## Status

Complete. The project administrator saved the private provider configuration
and confirmed that Google sign-in reaches `/dashboard`, including a repeat
sign-in after signing out.

## Existing Application Flow

- `/login` calls `signInWithOAuthProvider("google")`, which navigates to the
  server initiation route at `/auth/oauth/google`.
- The server stores the PKCE verifier through `Set-Cookie` before redirecting
  to Google and supplies
  `http://localhost:3000/auth/callback?next=%2Fdashboard` as `redirectTo`.
- `/auth/callback` exchanges the PKCE authorization code for the Supabase
  session, resolves redirects from `NEXT_PUBLIC_SITE_URL`, and permits only
  local relative `next` paths.
- A successful exchange redirects to `/dashboard`.

## Automated Results

- TypeScript (`npx tsc --noEmit`): PASS.
- ESLint (`npm run lint`): PASS with 11 pre-existing warnings and no errors.
- Redirect safety (`npx vitest run src/services/auth-redirect.test.ts`): PASS,
  7 cases covering safe local paths and external/backslash redirect rejection.
- Production build (`npm run build`): PASS.
- Public Supabase Auth settings: Google enabled after private provider setup.
- OAuth authorization endpoint: PASS; Supabase returns `302` to
  `accounts.google.com` and supplies
  `https://bnhylarpwbdwdrpctibn.supabase.co/auth/v1/callback` as Google's exact
  redirect URI.
- Callback-origin regression: the first browser test exposed a redirect to the
  development server's `0.0.0.0` bind address. Callback URL construction now
  uses the configured public app origin; regression checks confirm callback
  failures return to `http://localhost:3000/login`.
- PKCE exchange regression: Supabase Auth logs confirmed that Google login
  succeeded while repeated client-initiated attempts did not consistently
  reach `/token`. OAuth initiation now runs through a Next.js server route so
  its verifier is returned in `Set-Cookie` before the external redirect. The
  initiation service also adds the returned PKCE flow ID to the application
  callback as `sb_flow_id`; the callback passes it to the exchange so repeated
  or overlapping attempts cannot select a stale verifier.
- Dashboard authorization regression: successful Google exchanges returned
  `/token` and `/user` responses with status 200, but the dashboard redirected
  to `/login` because the existing Auth user had no `public.profiles` row.
  Migration `20261005032915_backfill_missing_auth_profiles.sql` repairs all
  missing profile rows idempotently.
- Profile RLS regression: the template-wide public profile read policy was
  removed by `20261005035320_harden_profiles_rls.sql`. Live verification shows
  RLS enabled with four authenticated-only policies: owners can select and
  update only their own row, while active administrators can select or update
  all profiles. Both update policies include matching `WITH CHECK` rules.
- Privilege-escalation regression:
  `20261005103200_prevent_profile_privilege_escalation.sql` limits direct
  authenticated updates to `full_name`, `age`, `birthday`, and `gender`.
  Live verification confirms `role` and `is_active` are not user-updatable,
  and `is_admin()` now requires an active administrator.
- Function privilege regression:
  `20261005111500_restrict_admin_function_execution.sql` removes the legacy
  anonymous execute grant from `is_admin()`.
- Service ownership defense: the non-administrator profile query also filters
  by the authenticated user's ID, requires active status for administrator
  access, and rebuilds profile update payloads from an explicit field allowlist.
- Supabase Security Advisor still reports project-wide hardening work outside
  P0.4: mutable function search paths, GraphQL object discoverability,
  executable security-definer functions, and disabled leaked-password
  protection. These warnings do not restore public profile row access and
  should be handled in a dedicated security task.
